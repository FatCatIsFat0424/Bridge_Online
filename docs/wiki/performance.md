# 效能與驗證

> [返回目錄](./index.md) · [系統架構](./architecture.md) · [任務 09](../tasks/09-performance.md) · 更新：2026-10-03

## 範圍與相容性

這次優化保留 JSON `schemaVersion: 1`、Repository 合約、HTTP / Socket payload、
帳號驗證、session 撤銷與遊戲規則，既有資料檔不需要遷移。
重點是減少查詢掃描、重複複製、無關房間的快照、未改變狀態的寫入及前端重複更新。

以下數字是效能優化完成時的量測快照，早於後續功能擴充；之後的 bundle 大小可能不同。
毫秒數受 CPU、磁碟、快取及背景負載影響，不能當成通用延遲保證。
回歸測試驗證結果、接收範圍、寫入次數和狀態等價，不設定執行時間門檻。

## 重現方式

從 repository 根目錄執行：

```bash
npm run bench:database
npm run bench:socket
npm run build:client
npm test
```

兩個 benchmark 都使用獨立暫存 JSON，不使用正式 `DATABASE_PATH`，完成後關閉並清理。
資料庫 benchmark 輸出 JSON，Socket benchmark 逐工作負載輸出 JSONL。
前端大小須將入口與所有啟動時預載的 JS / CSS 相加，再加上首個路由的 chunk。
新執行結果代表目前工作樹；下表的優化前數字是修改前同一工作負載的留存值。

## JSON repository

`database/indexes.ts` 以記憶體索引處理帳號 ID、正規化使用者名稱、session hash、
好友 ID / 帳號 / 無序帳號組合，以及每個帳號依時間排序的歷史。
索引依 collection 陣列身分按需建立及刷新；runtime 寫入不重建未改變的帳號索引。
有限筆數搜尋找到足夠結果即停止，回傳資料仍保持隔離。

寫入只複製會改變的 collection 陣列、替換紀錄與外部輸入。
Runtime coordinator 保留獨立回復快照，提交時使用受序列佇列保護的狀態檢視，
等待 repository 完成複製與保存後才執行下一個 action。

量測環境：Node.js 24.21.0；帳號、session、好友、歷史各 10,000 筆；
25 桌、100 位玩家、500 則聊天；檔案 14,054,061 bytes。
查詢與寫入列為暖機後三輪總時間的中位數，開檔時間為單次量測。

| 工作負載 | 優化前 ms | 優化後 ms |
| --- | ---: | ---: |
| 10,000 次帳號 ID 查詢 | 167.64 | 21.49 |
| 10,000 次使用者名稱查詢 | 239.81 | 19.89 |
| 10,000 次 session 查詢 | 263.28 | 17.61 |
| 1,000 次帳號好友查詢 | 92.70 | 3.61 |
| 1,000 次帳號歷史查詢 | 304.52 | 10.68 |
| 500 次有限筆數搜尋 | 237.09 | 7.70 |
| 5 次持久 runtime 寫入 | 929.13 | 310.36 |
| 開啟資料庫 | 58.85 | 60.87 |

開檔沒有改善。索引增加與資料量相關的記憶體成本，第一次存取或 collection 改變後仍需建立索引。
每次真正寫入仍驗證整份文件、序列化整份 JSON、寫暫存檔、執行 `fsync` 並原子替換。
大型資料的完整驗證與磁碟成本仍存在；這不是 SQL 或多程序協調的替代方案。
備份、單一程序限制與 SQL 遷移見[儲存說明](./accounts-and-storage.md)。

## Socket 與 runtime

每個 action 在序列化操作內記錄操作前、後的受影響帳號：操作者與其舊 / 新房間成員。
只對仍有連線的帳號 channel 傳送完整快照；同帳號的多個分頁都會收到。
離開、逾時清理和 profile 更新仍通知需要更新的原房間成員。
授權、驗證或保存失敗不廣播。

`player:resume` 繼續驗證 session、回覆明確 callback 並同步同房間快照。
Runtime 完全相同且沒有新完成對局時，可略過重複保存。
第一次附加玩家、最後分頁斷線、重新連線造成的真實變化仍會保存。

工作負載為三間房、每房四個不同帳號、每帳號一個 Socket 連線。
使用真實應用程式與 JSON repository，直接建立測試 session 以排除密碼雜湊成本。
快照數為 adapter 實際送往連線的次數；bytes 為 JSON payload UTF-8 位元組總和，
不含 Socket / WebSocket 框架、傳輸壓縮或 callback 封包。

| 工作負載 | 快照數 前 → 後 | Payload bytes 前 → 後 | Runtime 寫入 前 → 後 |
| --- | ---: | ---: | ---: |
| 一次聊天 | 12 → 4 | 13,488 → 5,200 | 1 → 1 |
| 十次未改變的 resume | 120 → 40 | 134,880 → 52,000 | 10 → 0 |
| 一次離開房間 | 12 → 4 | 11,937 → 3,649 | 1 → 1 |

此工作負載快照數減少約 67%，聊天 / resume 廣播 bytes 減少約 61%，離開房間減少約 69%。
單輪參考時間：聊天 3.90 → 3.74 ms、十次 resume 25.84 → 8.07 ms、離開 3.48 → 2.38 ms。
穩定的比較依據是快照、位元組及寫入次數。

## 前端

路由以 React `lazy` / `Suspense` 延後載入。Snapshot stores 保留相等欄位的既有物件，
只更新有變化的資料；頁面與元件使用所需的 store selector。
屬於其他帳號或無效的快照不套用到目前帳號。

大小單位沿用 Vite 報告的 kB；gzip 是建置時計算值，實際傳輸依伺服器設定。

| 範圍 | 優化前 raw / gzip kB | 優化後 raw / gzip kB |
| --- | ---: | ---: |
| 啟動 JS：入口加所有預載 chunk | 323.95 / 101.64 | 295.64 / 96.22 |
| 開啟登入頁的 JS 總量 | 323.95 / 101.64 | 299.00 / 97.45 |
| 啟動 CSS | 23.56 / 5.30 | 9.29 / 2.61 |

優化後入口為 190.52 / 60.28 kB，但須加上預載 JSX 18.17 / 7.25 kB
與 state 86.95 / 28.69 kB，不能只用入口大小宣稱收益。
登入頁另加 3.36 / 1.23 kB，因此實際登入 JS gzip 約減少 4.1%。
Game 路由延後的 JS 為 10.98 / 3.65 kB，CSS 為 6.93 / 1.94 kB；
這些內容仍會在進入對局時載入。

後續加入[玩家個人頁與音樂](./player-profiles-and-music.md)的整合建置：入口加全部預載 JS
為 300.65 / 98.54 kB，加登入路由後為 303.97 / 99.76 kB，初始 CSS 為 10.45 / 2.82 kB。
上表保留純效能階段的比較，避免把新增功能的大小與原量測混在一起。

舊流程每筆快照執行七次 store setter，100 筆相同快照共 700 次。
新回歸測試確認 100 筆相同快照不通知訂閱者，僅聊天變動時只通知 chat store 一次。
這是 store 層證據，不是整個 React 畫面的渲染時間量測。

## 功能保留證據

- Repository 測試涵蓋索引刷新、輸入 / 回傳隔離、限制筆數、並行操作與失敗回復。
- Socket 測試比對受影響玩家的廣播與 resume callback 完整內容，驗證無關房間不收到更新。
- 多分頁、首次連線、斷線與重連測試驗證真正需要持久化的動作。
- 完整對局測試涵蓋私人手牌、重啟、出完 52 張牌、歷史保存與撤銷 session。
- 前端測試涵蓋相同快照、聊天單獨變更、profile 變更、狀態清除及帳號隔離。
- 瀏覽器已確認登入、既有路由、語系、房間選座 / 聊天 / 重新整理 / 準備 / 離開及登出。

最終檢查使用 TypeScript、ESLint、Vitest 和前端正式建置，測試數量以當次輸出為準。
